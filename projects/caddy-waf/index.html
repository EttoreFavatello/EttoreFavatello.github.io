WAF Reverse Proxy

Reverse proxy Caddy con Web Application Firewall (Coraza + OWASP Core Rule Set), terminazione TLS e load balancing su due backend. Tutto il traffico viene ispezionato prima di raggiungere i server, invisibili dall'esterno.

[ ← home ] [ codice su github ]

// Nota

Progetto sviluppato in ambiente di laboratorio a scopo didattico, costruito insieme al docente durante il percorso ITS. Il dominio lab.local e i backend che rispondono "A" e "B" sono artifici per rendere osservabile il comportamento dello stack.

// Overview

Un WAF in reverse proxy: tutto il traffico entra da Caddy, che prima lo fa ispezionare a Coraza contro le regole OWASP CRS, e solo se supera il controllo lo inoltra — bilanciato — a uno dei due backend. Se la richiesta è ostile, viene bloccata con un 403 Forbidden prima ancora di raggiungere il backend.

L'obiettivo del progetto non è solo far funzionare lo stack, ma saperlo leggere, interrogare e capire nei suoi limiti — la mentalità difensiva che serve a un analista SOC per riconoscere cosa un WAF vede e cosa può aggirare.

// Architettura

Caddy è l'unico servizio esposto. La richiesta segue questo flusso:

  • Il client si connette in HTTPS su lab.local (TLS terminato da Caddy)
  • La direttiva order coraza_waf first fa ispezionare la richiesta a Coraza prima di ogni altra cosa
  • Se la richiesta è ostile → 403, il backend non la vede mai
  • Se è pulita → prosegue al reverse_proxy, che la bilancia su backend-a o backend-b

// Componenti

01
WAF in reverse proxy
Ispezione della richiesta contro le regole OWASP CRS prima dell'inoltro. Il backend riceve solo traffico già filtrato.
02
Health check attivi
Caddy testa i backend ogni 5 secondi e li toglie dalla rotazione se non rispondono con un 200, prima che un utente ne paghi il guasto.
03
Regole custom
Una regola deny diretta (blocco immediato) e una pass + setvar che contribuisce all'anomaly score del CRS, per capire i due modelli di decisione.

// Tool utilizzati

tool
Caddy
Reverse proxy che termina il TLS, bilancia il carico e ospita il WAF. Unico servizio esposto all'esterno.
tool
Coraza
Motore Web Application Firewall compatibile con SecLang, erede open source di ModSecurity, integrato in Caddy.
tool
OWASP CRS
Core Rule Set: set di regole di sicurezza basato su anomaly scoring, che assegna punti agli indizi di attacco fino a una soglia di blocco.
tool
Docker Compose
Orchestrazione dei container dello stack: Caddy e i due backend nginx su rete interna isolata.
tool
nginx
I due backend dietro il proxy, ciascuno serve una pagina distinguibile ("A" e "B") per rendere osservabile il load balancing.
tool
xcaddy
Build tool per compilare Caddy con il modulo Coraza incluso, tramite un Dockerfile multi-stage.

// Highlight — Load balancing analizzato sui dati reali

Un dettaglio poco noto: il comportamento di default del load balancing di Caddy non è il round robin (come in NGINX), ma la politica random. L'ho verificato empiricamente registrando 1000 richieste reali:

  • 472 risposte da A, 528 da B — non 500/500 netti: è la normale fluttuazione statistica di 1000 scelte casuali
  • Lo stesso backend risponde spesso due volte di fila (AA=210, BB=266) — cosa che il round robin renderebbe impossibile

Portare dati misurati a sostegno di un'affermazione tecnica, invece di ripetere quello che dice un manuale, è esattamente la mentalità che distingue un'analisi da un'opinione.
